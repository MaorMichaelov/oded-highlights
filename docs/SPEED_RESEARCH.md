# Speed to publish (agent report, 17 Nov 2026; WebFetch blocked, search summaries only; F=fact, E=estimate, U=unverified)
- Does being first matter? No hard data. U: vendors claim it; Shorts can be rewarded days later; E: first matters for unambiguous searchable moments (reveal, famous guest, fight, a trailer reaction), little for generic funny clips. Treat speed as a tiebreaker and measure it.
- Twitch: Helix /clips with narrow windows every 20-30 s + view velocity (views/min since created_at) = highlight trigger (Twitch only; Kick has no equivalent -> chat/audio spikes). Date filtering is flaky: use <= 1 day windows and paginate.
- Kick: HLS EVENT playlist while live (we already read it); a rolling buffer + cut from the buffer is the fastest design. Segment length/DVR depth undocumented: inspect a live playlist.
- ASR only on candidate windows: Groq whisper-large-v3-turbo ~216x realtime (60 s window ~0.3 s + network); free tier ~20 RPM / 7200 audio s per hour (verify).
- Render: Shorts need 9:16 re-encode anyway; x264 ultrafast/30 fps/threads 4 gives ~3-5x realtime on 4 vCPU (E): a 40 s Short in ~10-25 s. Benchmark on the runner.
- YouTube: F: API projects created after 28 Jul 2020 without a passed compliance AUDIT get videos.insert uploads forced PRIVATE (our model - private drafts + manual publish by the owner/Grok - is unaffected, but fully automatic public publishing needs the audit); upload of an 8 MB Short 5-15 s; ~0.5-2 min until watchable. Default quota ~100 uploads/day (docs conflict).
- GitHub Actions: 20 concurrent jobs, 6 h per job, public-repo runners 4 vCPU/16 GB/14 GB disk; cron is delayed 5-20 min (do not rely on it); a warm watcher that re-arms itself (what live-loop.yml does) is the right design; possible abuse flags for 24/7 jobs (check ToS).
- Latency budget (E): stream 5-15 s + detection 10-40 s + (wait for moment end 10-30 s, skip by shipping a provisional clip) + cut 1-3 s + ASR 1-3 s + LLM 1-3 s + render 10-25 s + upload 5-20 s + YouTube processing 30-120 s = ~1.5-4 min total, target <= 5 min.
- Priority: (1) API audit/verification if automatic public publishing is wanted; (2) warm watcher with rolling buffer; (3) cheap triggers, ASR/LLM only on candidates; (4) provisional fast Short, parallel ASR+LLM; (5) only top-scored moments; (6) benchmark dispatch latency, Kick segment length, x264 fps.

## Measured on the real pipeline (17 Nov)
- Per clip stage times (Hebrew pipeline): CUT is the bottleneck: ~0.4-0.5x the clip length (19 min clip: 584 s; 93 min: 2282 s); EDIT ~100-190 s fixed; QUALITY 3-50 s; upload 5-80 s (93 min: 731 s).
- SMART CUT (scripts/build_clip.py, `fast: true` in cuts.json): re-encode only the edges, stream-copy whole HLS segments in between (Kick 1080p60 = 9.2 Mbps nominal, measured 8.4 Mbps on a 150 s test: close to the 8 Mbps gate; below it the final is re-encoded once). 19.4 min clip: CUT 3 min 12 s instead of 9 min 44 s (3x); verified by a full decode + duration check, falls back to the full re-encode.
- LIMITATION found by bisecting: a smart-cut body breaks the opening compositor (peak_open/nov13_open.py: final video 946 s vs audio 161 s, SYNC FAIL), the normal re-encoded body passes. So `fast` is enabled ONLY for English/unbranded clips (WORLD CLIPS), which skip the opening.
